How payment works

x402 turns HTTP status 402 into a payment step that software can complete on its own.

  1. Ask. Call an endpoint. The server answers 402 Payment Required and lists the price, the asset (USDC) and the network.
  2. Pay. Your x402 client signs a USDC authorization. No gas, no wallet popup, no account.
  3. Receive. The payment is settled first, then the data is fetched exactly once and returned with a receipt.

Inputs are validated before a price is quoted, so you are never asked to pay for a request we cannot serve. Retrying the same payment returns the stored result and never charges twice.

3 · Approve one purchase

Follow the REST and MCP purchase guide. Its downloadable example starts with a free preview and requires an explicit spending limit before signing one payment. It checks the merchant, network, USDC contract, price and resource.

If payment or delivery is unclear, keep the existing purchase record and retrieve its result. Do not create a new payment just to recover an answer.

Parameters

location_code is a country-level DataForSEO code (2840 United States, 2276 Germany, 2826 United Kingdom). language_code is optional (en, de, …). Unsupported combinations are rejected with HTTP 422 before any payment is requested.

MCP (Model Context Protocol)

Streamable HTTP endpoint: {{BASE_URL}}/mcp

Free tools work with any MCP client: list_services, preflight, get_result, retry_request. The paid tools (one per service) need a client that supports x402 payments, for example one built with @x402/mcp. A client without payment support can still list and inspect the tools; a paid call then returns a "payment required" result and charges nothing.
